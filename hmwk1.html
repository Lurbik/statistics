Private key to public key with elliptic-curve scalar multiplication

A toy version of what Ethereum does with the curve secp256k1: the curve y² = x³ + 7 over the integers mod 17, computed step by step. Educational only: this curve has 18 points and offers no security.

1. The idea

We work on the toy curve y² = x³ + 7 (mod 17) (same equation as secp256k1, but over the tiny field of the integers 0…16). The points of the curve, together with a special "point at infinity" O, form a group with an addition rule P + Q. Given a base point G and a private key k (an integer), the public key is

Q = kG = G + G + … + G (k times)

Computing Q from k is easy; recovering k from Q, i.e. solving Q = kG for k, is the Elliptic Curve Discrete Logarithm Problem (ECDLP). On a real curve no algorithm is known that does it much faster than about √n trials, where n is the number of points generated by G. This makes k → kG a one-way function.

Ethereum (and Bitcoin) use the curve secp256k1 ("Standards for Efficient Cryptography, prime field, 256 bits, Koblitz curve no. 1"): the same equation y² = x³ + 7, but modulo the prime p = 2²⁵⁶ − 2³² − 977, with a base point G of order n ≈ 1.16·10⁷⁷. A private key is a random k in [1, n − 1]; its public key is Q = kG.

Point addition (all operations mod 17). There is no division modulo p: dividing by d means multiplying by the modular inverse d⁻¹, the number with d·d⁻¹ ≡ 1 (mod p), which exists because p is prime.

P ≠ Q (chord): λ = (y₂ − y₁) · (x₂ − x₁)⁻¹ mod p
P = Q (tangent): λ = (3x₁² + a) · (2y₁)⁻¹ mod p
x₃ = λ² − x₁ − x₂ mod p y₃ = λ(x₁ − x₃) − y₁ mod p
Special cases: P + O = P, P + (−P) = O (vertical line), where −(x, y) = (x, −y)

2. Compute the public key




  Repeated addition computes G, 2G, 3G, …, kG: k − 1 additions, impossible for a 256-bit k.
  Double-and-add writes k in binary and only uses the multiples G, 2G, 4G, 8G, … (each one is the double of the previous):
  for k = 6 = 110₂ it computes 6G = 2G + 4G. It needs about 2·log₂k operations, i.e. at most ≈ 512 for a 256-bit key.
  Both methods give the same Q. Since nG = O, the result only depends on k mod n (for G = (1, 5), n = 9: 6G = 15G = 24G = …).

4. Statistical exploration



  We treat the map k → kB as a black box and look at its outputs as data, for every private key k = 1 … n−1.
  Here n is the order of the base point B: the smallest n with nB = O. It is found by adding B to itself until O appears
  (this happens when we add a point to its opposite, e.g. 8G = (1, 12) = −G, so 9G = 8G + G = O). After that the outputs repeat:
  kB = (k mod n)B. By Lagrange's theorem the order divides the number of points of the curve (18), so it can only be
  1, 2, 3, 6, 9 or 18. G = (1, 5) has order 9; the points of order 18, such as (15, 13), generate the whole curve.




  
  







5. Discussion



What the experiments show (base point G = (1, 5), k = 1 … 8)


    
  
  • Periodicity. G has order 9: 9G = O and then the outputs repeat (10G = G, 15G = 6G, …), so only 8 different public keys
      exist. Different private keys giving the same public key (k ≡ k' mod n) is a weakness of a tiny group, not a security feature:
      on secp256k1, n ≈ 1.16·10⁷⁷ and private keys are taken in [1, n − 1], where every k gives a different Q.
    • 
  
  • Distribution and frequencies. kG and (9−k)G are opposite points (same x, opposite y), so the x-values come in pairs:
      only 4 of the 17 possible x-values occur (1, 2, 5, 12, twice each), while y takes 8 different values once each.
      The coordinates are not uniform over 0…16. With the generator (15, 13) of order 18, y takes all 17 values exactly once,
      but x still only 9: the pairing of x is unavoidable.
    • 
  
  • Bits and entropy. Only 33% of the output bits are 1 instead of 50%. Part of this bias comes from the 5-bit encoding of the
      values 0…16 (uniform values would give 39%), the rest from the few values reached. The entropy is 2 bits for x and 3 bits for y,
      against a maximum of log₂17 ≈ 4.09 bits.
    • 
  
  • Correlation. We measured r(k, x) = 0.00 and r(k, y) = 0.30. The value 0 for x is a consequence of the symmetry: the sequence
      of x-values 1, 2, 5, 12, 12, 5, 2, 1 rises and then falls, so the two halves cancel. Yet x is completely determined by k:
      no linear correlation does not mean independence, and the small sample (8 points) makes r for y not significant either.
    • 
  
  • Avalanche. Flipping one bit of k changes on average 4.39 of the 10 output bits (44%), not far from the 50% of SHA-256.
      It looks hash-like, but the outputs are algebraically linked: (a + b)G = aG + bG held in all 400 tests.
      For example, from a public key Q = kG anyone can compute the public key of k + 1, Q + G, without knowing k.
    • 




Properties meaningful for a cryptographic one-way function


    
  
  • Deterministic and efficient forward computation (double-and-add: ≈ 2·log₂k operations).
    • 
  
  • Hard inversion: the ECDLP. There is no way to "divide" Q by G, and the coordinates of kG give no hint of how large k is,
      so an attacker can only search. The best generic attacks are baby-step giant-step (store the m ≈ √n points G, 2G, …, mG,
      then subtract mG from Q repeatedly until a stored point appears: k = j·m + i) and Pollard's rho (a pseudo-random walk over
      points aG + bQ that, by the birthday paradox, repeats after ≈ √n steps; the repetition gives an equation for k, with almost no memory).
      Both need ≈ √n operations: ≈ 2¹²⁸ for secp256k1, far beyond any computer, while here trying the 8 possible keys is instant.
    • 
  
  • A large group order n, and no collisions: k → kG is one-to-one for k = 1 … n−1.
    • 
  
  • Uniformity in the sense of the group: if k is chosen uniformly at random, kG is a uniformly random point of the subgroup,
      so an attacker learns nothing from which point Q is.
    • 
  
  • The algebraic structure is a feature: it makes digital signatures (ECDSA, Elliptic Curve Digital Signature Algorithm, used to sign
      every Ethereum transaction) and key exchange (ECDH, Elliptic Curve Diffie–Hellman: a(bG) = b(aG) gives two parties a shared secret) possible.
    • 




Properties specifically associated with cryptographic hash functions


    
  
  • Any-length input → fixed-length output; preimage, second-preimage and collision resistance.
    • 
  
  • Strong avalanche effect: each output bit flips with probability ½ when one input bit changes.
    • 
  
  • Output statistically indistinguishable from random, with no algebraic relation between H(a), H(b), H(a+b).
    • 
  
  • For hashes, uniform bits, no correlation and avalanche are meaningful necessary (not sufficient) tests.
    • 
  
  • A hash alone cannot replace the curve: with "public key = SHA-256(k)" nobody could verify a signature or agree on a shared secret
      without learning k, because a hash has no structure to exploit.
    • 




Conclusion



  Statistical "randomness" of the coordinates tells us little about the security of elliptic-curve cryptography:
  its security comes from the computational hardness of the ECDLP on a huge group, and the function deliberately keeps
  its algebraic structure. Avalanche, pseudo-random output and absence of structure are the design goals of hash functions.
  This is why Ethereum combines both: the public key Q is hashed with Keccak-256 to obtain the address (HMWK 2).
