HMWK 2 — From wallet seed to Ethereum address

Hashing, key derivation and cryptographic primitives in an Ethereum HD wallet, with their statistical properties. Every value on this page is computed live in the browser (ethers.js). It builds on HMWK 1: step 4 of the pipeline is exactly the scalar multiplication Q = kG implemented there, on the real curve instead of the toy one.

4. Role of each standard and primitive

  • BIP-39 — turns 128–256 random bits into 12–24 words from a list of 2048 = 2¹¹ words (11 bits per word). A checksum (the first bits of SHA-256 of the entropy) is appended, so a wrong word is usually detected. The words are then stretched into a 512-bit seed with PBKDF2-HMAC-SHA512 (salt "mnemonic" + passphrase, 2048 iterations), which slows down brute force. Purpose: a human-readable backup.
  • BIP-32 — hierarchical deterministic (HD) derivation. HMAC-SHA512 of the seed gives a master private key and a chain code; every child key is computed from its parent. One backup protects an unlimited tree of keys. With non-hardened derivation, public child keys can be derived from the parent public key alone (watch-only wallets): child key = parent key + t, so child public key = parent public key + t·G, the property (a + b)G = aG + bG observed in HMWK 1, section 4.
  • BIP-44 — a convention for the tree: m / purpose' / coin_type' / account' / change / index. For Ethereum: m/44'/60'/0'/0/i. This is why the same mnemonic gives the same accounts in MetaMask, Rabby, Exodus, …
  • secp256k1 — the real version of the HMWK 1 toy curve: same equation y² = x³ + 7, but modulo a 256-bit prime (curve, point addition, double-and-add and why inverting Q = kG is infeasible: HMWK 1, sections 1–2 and 5). Private keys sign transactions with ECDSA.
  • Keccak-256 — hash of the 64-byte public key X‖Y; the last 20 bytes form the address: short, fixed length, and the public key itself stays hidden until the first signed transaction.
  • EIP-55 — hides a checksum in the letter case of the hex address: a letter is uppercase when the corresponding hex digit of Keccak-256(lowercase address) is ≥ 8. Backward compatible: an all-lowercase address is still valid, just unchecked.

5. Statistical properties

The hash-based steps (PBKDF2, HMAC-SHA512, Keccak-256) should behave like random functions: balanced bits, uniform hex digits, avalanche effect, unrelated outputs for related inputs. For them these tests are meaningful. secp256k1 instead keeps an algebraic structure (HMWK 1, section 5): its security comes from the discrete-logarithm problem, not from statistical randomness. Old, well-studied primitives (public-key cryptography, hash functions) come first; the newer standards on top solve usability problems: backup, many accounts from one secret, typo detection.

7. SHA-2 / SHA-512 vs Keccak / SHA-3

  • SHA-2 uses the Merkle–Damgård construction (a compression function applied block by block). It is still secure, but vulnerable to length-extension attacks, which is why it is used inside HMAC.
  • Keccak uses a completely different design, the sponge construction (a 1600-bit state that "absorbs" the input and is then "squeezed" to produce the output). It won the NIST SHA-3 competition in 2012.
  • Keccak-256 ≠ SHA3-256. In the final standard (FIPS 202, 2015) NIST added a domain-separation suffix, so the padding byte changed from 0x01 (Keccak) to 0x06 (SHA-3). Ethereum had already adopted the original Keccak. Same permutation, different padding → different outputs:

8. Why several techniques instead of one?

Each step solves a different problem, and no single primitive has all the required properties:

  • BIP-39 / BIP-32 / BIP-44 → key management: one human-readable backup, reproducible derivation of many keys, compatibility between wallets.
  • secp256k1 → public/private key relationship and signatures: a hash cannot sign; signing needs a key pair with algebraic structure (the homomorphism of HMWK 1).
  • Keccak-256 → hashing: a short, fixed-length, uniform identifier that removes the structure of the public key.
  • EIP-55 → error detection: cheap protection against typos, with no security claim against attackers.

Separating the roles also lets each component be analysed, standardised and, if needed, replaced independently.

9. Practical check with a wallet

Importing the test mnemonic test test … junk into MetaMask (in a separate test browser profile) shows as first account 0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266, the same address computed above with index 0: the wallet follows exactly BIP-39 → BIP-32 → BIP-44 (m/44'/60'/0'/0/i) → secp256k1 → Keccak-256 → EIP-55, including the EIP-55 letter case. Further accounts correspond to increasing the index i. Creating a new wallet is the only generation step; restoring from the words is pure derivation.

The same screenshot also shows Bitcoin, Solana, Tron and Stellar addresses derived from the same 12 words. This is the key-management layer (BIP-39 / BIP-32 / BIP-44) at work: one seed, different coin_type values in the path (0 for Bitcoin, 60 for Ethereum, …), and then each blockchain applies its own curve, hash and encoding. The seed is shared; the cryptographic primitives after it are chain-specific.
